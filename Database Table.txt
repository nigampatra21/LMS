Yes. For now, **one MySQL database is completely fine**, especially while you're learning/building the first version. Don't over-engineer this with multiple databases yet.

We'll create **one `lottery_db`** and build the tables in dependency order.

# Step 5 — Create `lotteries`

```sql
CREATE TABLE lotteries (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,

    lottery_code VARCHAR(50) NOT NULL UNIQUE,
    name VARCHAR(150) NOT NULL,
    description TEXT,

    ticket_price DECIMAL(12,2) NOT NULL,

    currency VARCHAR(3) NOT NULL DEFAULT 'INR',

    status VARCHAR(30) NOT NULL DEFAULT 'DRAFT',

    sales_start_at DATETIME NOT NULL,
    sales_end_at DATETIME NOT NULL,
    draw_at DATETIME NOT NULL,

    max_tickets BIGINT,

    created_by BIGINT NOT NULL,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    CONSTRAINT chk_ticket_price
        CHECK (ticket_price > 0),

    CONSTRAINT chk_lottery_dates
        CHECK (
            sales_start_at < sales_end_at
            AND sales_end_at <= draw_at
        ),

    CONSTRAINT fk_lottery_created_by
        FOREIGN KEY (created_by)
        REFERENCES users(id)
);
```

Here we're deliberately using a foreign key because we're currently using **one database**.

# Step 8 — Create `tickets`

```sql
CREATE TABLE tickets (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,

    ticket_id VARCHAR(50) NOT NULL UNIQUE,

    lottery_id BIGINT NOT NULL,

    customer_id BIGINT,
    agent_id BIGINT,

    ticket_number VARCHAR(100) NOT NULL,

    price DECIMAL(12,2) NOT NULL,

    status VARCHAR(30) NOT NULL DEFAULT 'ISSUED',

    purchased_at DATETIME NOT NULL,
    issued_at DATETIME,

    cancelled_at DATETIME,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    CONSTRAINT uq_lottery_ticket_number
        UNIQUE (lottery_id, ticket_number),

    CONSTRAINT fk_ticket_lottery
        FOREIGN KEY (lottery_id)
        REFERENCES lotteries(id),

    CONSTRAINT fk_ticket_customer
        FOREIGN KEY (customer_id)
        REFERENCES users(id),

    CONSTRAINT fk_ticket_agent
        FOREIGN KEY (agent_id)
        REFERENCES users(id),

    INDEX idx_ticket_lottery (lottery_id),
    INDEX idx_ticket_customer (customer_id),
    INDEX idx_ticket_agent (agent_id),
    INDEX idx_ticket_status (status)
);
```

SELECT
    l.id,

```sql
SELECT
    l.name AS lottery,
    p.tier_number,
    p.tier_name,
    p.prize_amount,
    p.winner_count
FROM lotteries l
JOIN prize_tiers p
    ON p.lottery_id = l.id
WHERE l.id = 1
ORDER BY p.tier_number;
```

## Our database is now ready

The dependency structure is:

```text
users
  │
  ├── roles
  │
  └── lotteries
          │
          ├── lottery_rules
          │
          ├── prize_tiers
          │
          ├── tickets
          │      │
          │      └── ticket_transactions
          │
          └── draws
                  │
                  └── winning_numbers
                         │
                         ▼
                      winners
                         │
                         ▼
                    prize_claims
```

### One thing I would change from the earlier architecture

Since you're using **one MySQL database right now**, don't pretend we're already running a fully independent database-per-service architecture. That's unnecessary complexity.

We'll use **logical microservice ownership**:

```text
auth-service       → users, roles
lottery-service    → lotteries, prize_tiers, lottery_rules
ticket-service     → tickets, ticket_transactions
draw-service       → draws, winning_numbers
winner-service     → winners, prize_claims
```

All currently happen to live inside `lottery_db`.

Later, when the application is mature, we can split the databases if there's a real operational reason.
