# Step 3 — Database Design

We'll use **MySQL with one database per microservice**.

The most important rule:

> **A microservice owns its database. Another service must never directly query or modify that database.**

For example, `ticket-service` can store `lottery_id`, but it must not create a MySQL foreign key into `lottery_db`.

---

# 1. Database architecture

We'll start with six databases:

```text
lottery_system
│
├── auth_db
├── lottery_db
├── ticket_db
├── draw_db
├── winner_db
└── audit_db
```

Later, reporting can have its own read-optimized database.

## `users`

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(100) NOT NULL UNIQUE,
    email VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    first_name VARCHAR(100),
    last_name VARCHAR(100),
    phone VARCHAR(20),
    status VARCHAR(30) NOT NULL DEFAULT 'ACTIVE',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP
);
```

Status:

```text

INACTIVE
```

## `user_roles`

```sql
CREATE TABLE user_roles (
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,

    PRIMARY KEY (user_id, role_id),

    CONSTRAINT fk_user_roles_user
        FOREIGN KEY (user_id) REFERENCES users(id),

    CONSTRAINT fk_user_roles_role
        FOREIGN KEY (role_id) REFERENCES roles(id)
);
```

---

## `role_permissions`

```sql
CREATE TABLE role_permissions (
    role_id BIGINT NOT NULL,
    permission_id BIGINT NOT NULL,

    PRIMARY KEY (role_id, permission_id),

    CONSTRAINT fk_role_permissions_role
        FOREIGN KEY (role_id) REFERENCES roles(id),

    CONSTRAINT fk_role_permissions_permission
        FOREIGN KEY (permission_id) REFERENCES permissions(id)
);
```

So:

```text

  ↓
ROLE
  ↓
PERMISSION
```

Example:


# 4. `lotteries`

```sql
CREATE TABLE lotteries (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    lottery_code VARCHAR(50) NOT NULL UNIQUE,
    name VARCHAR(150) NOT NULL,

    description TEXT,

    ticket_price DECIMAL(12,2) NOT NULL,

    currency VARCHAR(3) NOT NULL DEFAULT 'INR',

    status VARCHAR(30) NOT NULL DEFAULT 'DRAFT',

    sales_start_at DATETIME NOT NULL,
    sales_end_at DATETIME NOT NULL,
    draw_at DATETIME NOT NULL,

    max_tickets BIGINT,

    created_by BIGINT NOT NULL,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    CONSTRAINT chk_ticket_price
        CHECK (ticket_price > 0),

    CONSTRAINT chk_lottery_dates
        CHECK (
            sales_start_at < sales_end_at
            AND sales_end_at <= draw_at
        )
);
```

Notice:

```text
created_by BIGINT
```

There is **no foreign key to `auth_db.users`**.

Why?

Because `auth_db` belongs to another microservice.

We'll store the user ID as a logical reference.

# 5. Lottery status

We'll use:

```text
DRAFT
SCHEDULED
ACTIVE
SALES_CLOSED
DRAW_PENDING
DRAW_COMPLETED
SETTLED
CANCELLED
```

We'll enforce legal transitions in Java.

For example:

```text
DRAFT
 ↓
SCHEDULED
 ↓
ACTIVE
 ↓
SALES_CLOSED
 ↓
DRAW_PENDING
 ↓
DRAW_COMPLETED
 ↓
SETTLED
```

We should **not** let an API client arbitrarily change:

```text
SETTLED → ACTIVE
```

# 6. `prize_tiers`

```sql
CREATE TABLE prize_tiers (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    lottery_id BIGINT NOT NULL,

    tier_number INT NOT NULL,

    tier_name VARCHAR(100) NOT NULL,

    prize_amount DECIMAL(15,2) NOT NULL,

    winner_count INT NOT NULL,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uq_lottery_tier
        UNIQUE (lottery_id, tier_number),

    CONSTRAINT chk_prize_amount
        CHECK (prize_amount >= 0),

    CONSTRAINT chk_winner_count
        CHECK (winner_count > 0)
);
```

Notice again:

```text
lottery_id
```

is not a foreign key.

It is owned by the Lottery Service.

# 7. Example prize configuration

```text
lottery_id = 1

tier 1 → ₹10,00,000 → 1 winner
tier 2 → ₹1,00,000  → 5 winners
tier 3 → ₹10,000    → 50 winners
tier 4 → ₹1,000     → 500 winners
```

This gives us flexibility.

We don't need Java code like:

```java
if (tier == 1) {
    prize = 1000000;
}
```

That's bad design.

# 11. `tickets`

```sql
CREATE TABLE tickets (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    ticket_id VARCHAR(50) NOT NULL UNIQUE,

    lottery_id BIGINT NOT NULL,

    customer_id BIGINT,

    agent_id BIGINT,

    ticket_number VARCHAR(100) NOT NULL,

    price DECIMAL(12,2) NOT NULL,

    status VARCHAR(30) NOT NULL,

    purchase_reference VARCHAR(100),

    purchased_at DATETIME NOT NULL,

    issued_at DATETIME,

    cancelled_at DATETIME,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    CONSTRAINT uq_lottery_ticket_number
        UNIQUE (lottery_id, ticket_number),

    INDEX idx_ticket_lottery (lottery_id),

    INDEX idx_ticket_customer (customer_id),

    INDEX idx_ticket_agent (agent_id),

    INDEX idx_ticket_status (status)
);
```

Important:

```sql
UNIQUE (lottery_id, ticket_number)
```

This prevents the same ticket number from being issued twice within a lottery.

# 25. Why we don't use cross-database foreign keys

Suppose:

```text
ticket_db.tickets.lottery_id
```

references:

```text
lottery_db.lotteries.id
```

That creates tight coupling.

Instead:

```text
ticket_db
tickets
-----------------
lottery_id = 1001
```

The Ticket Service can ask:

```http
GET /api/lotteries/1001
```

when it needs lottery information.

This gives us independent services.

# 26. Indexing strategy

We're not going to blindly put indexes on every column.

Important indexes include:

```text
lottery_code
lottery status
lottery dates

ticket_id
lottery_id
customer_id
agent_id
ticket status

draw_id
lottery_id
draw status

winner_id
ticket_id
customer_id

audit resource
audit user
audit timestamp
```

Indexes improve reads but make writes more expensive and consume storage.

# 28. One important improvement

I don't want us to rush into creating JPA entities for every table yet.

First we'll define the **API contracts and domain boundaries**.

Otherwise we can end up with anemic entities and services that simply do:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

without real business logic.

Our goal is:

```text
HTTP
 ↓
Controller
 ↓
Application Service
 ↓
Domain/business rules
 ↓
Repository
 ↓
Database
```
