# 2. Microservice responsibilities

We don't want overlapping responsibilities.

### Auth Service

Owns:

```text
User
Role
Permission
Authentication
JWT
Refresh Token
Password
```

It answers:

> "Who is this user and what are they allowed to do?"

---

### Lottery Service

Owns:

```text
Lottery
Lottery Rules
Prize Tier
Lottery Schedule
Lottery Status
```

It answers:

> "What lottery exists and what are its rules?"

---

### Ticket Service

Owns:

```text
Ticket
Ticket Purchase
Ticket Cancellation
Ticket Status
```

It answers:

> "Which tickets have been issued?"

---

### Draw Service

Owns:

```text
Draw
Draw Schedule
```

It answers:

> "What draw happened and what was its result?"

---

### Winner Service

Owns:

```text
Winner

```

It answers:

> "Who won and what happened to the prize?"

---

### Notification Service

Owns:

```text
Email
SMS

```

It answers:

> "Who needs to be notified?"

---

### Reporting Service

Owns:

```text
Sales reports

```

---

### Audit Service

```text

New value

```

This is especially important for administrative operations.

# 3. Database-per-service

This is a major microservice principle.

Don't do this:

```text
                    ┌──────────────┐
                    │   MySQL      │
                    │              │
                    │ ALL TABLES   │
                    └──────────────┘
                      ▲ ▲ ▲ ▲ ▲
                      │ │ │ │ │
                     all services
```

Instead:

```text
Auth Service
     │
     ▼
 auth_db

Lottery Service
     │
     ▼
 lottery_db

Ticket Service
     │
     ▼
 ticket_db

Draw Service
     │
     ▼
 draw_db

Winner Service
     │
     ▼
 winner_db
```

This prevents one service from directly modifying another service's data.

# 4. How services communicate

There will be **two types of communication**.

## Synchronous — REST

Use REST when the caller needs an immediate answer.

Example:

```text
Frontend
   │
   ▼
Gateway
   │
   ▼
Lottery Service
   │
   ▼
Response
```

For example:

```http
GET /api/lotteries/LOT-001
```

---

## Asynchronous — Kafka

Use Kafka when something has happened and other services need to react.

Example:

```text
Ticket Service
      │
      │ TicketPurchasedEvent
      ▼
    Kafka
      │
      ├──────► Notification
      │
      ├──────► Reporting
      │
      └──────► Audit
```

The Ticket Service doesn't wait for all three services.

That's the key difference.

# 7. Important: don't let Draw Service modify Ticket DB

Bad architecture:

```text
Draw Service
     │
     └──────► ticket_db
```

Good architecture:

```text
Draw Service
     │
     ▼
Ticket Service API
```

or preferably through an event/contract appropriate to the operation.

Each service owns its data.

# 9. JWT security architecture

The flow will be:

```text
                   Login
                     │
                     ▼
              ┌─────────────┐
              │Auth Service │
              └──────┬──────┘
                     │
                     ▼
                  JWT
                     │
                     ▼
                React App
                     │
                     │ Bearer Token
                     ▼
               API Gateway
                     │
                     ▼
              Microservice
```

We'll validate the token at the gateway and enforce authorization at the service level too.

Why both?

Because relying exclusively on the gateway is dangerous.

A service should still protect itself.

# 13. Handling duplicate ticket purchases

This is a real-world problem.

Imagine two requests arrive simultaneously:

```text
Request A ─┐
           ├── Ticket number A
Request B ─┘
```

We need to prevent duplicate issuance.

We'll use a combination of:

```text
Database constraints
Transactions
Idempotency keys
Proper locking where necessary
```

For example:

```http
POST /api/tickets

Idempotency-Key: 5d8c9...
```

If the same request is submitted twice, the system shouldn't create two tickets.

# 14. Distributed transaction problem

Suppose:

```text
Ticket Service
     ↓
Payment
     ↓
Ticket created
     ↓
Kafka event
```

What happens if payment succeeds but ticket creation fails?

Or:

```text
Ticket created
     ↓
Kafka unavailable
```

We need to handle these failures.

We'll eventually use patterns such as:

### Transactional Outbox

```text
Ticket DB
 ┌──────────────────────┐
 │ tickets              │
 │ outbox_events        │
 └──────────┬───────────┘
            │
            ▼
       Kafka Publisher
            │
            ▼
          Kafka
```

This is much more reliable than:

```java
saveTicket();
kafka.send();
```

and assuming both always succeed.

# 16. Failure handling

We'll explicitly design for failure.

Example:

```text
Ticket Service
      │
      ▼
Kafka unavailable
```

We shouldn't lose the event.

The Outbox pattern will help.

Another:

```text
Notification Service DOWN
```

Ticket purchase should **not necessarily fail** just because email service is unavailable.

That's why asynchronous communication is useful.
