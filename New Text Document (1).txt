# 3. Don't start with 15 microservices

This is where many developers make a bad architectural decision.

They create:

```text
user-service
auth-service
lottery-service
ticket-service
payment-service
winner-service
notification-service
report-service
agent-service
admin-service
...
```

before writing a single business rule.

That's unnecessary complexity.

I would start with **5–6 well-defined services**:

```text
                    ┌─────────────────┐
                    │    React UI     │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │   API Gateway   │
                    └────────┬────────┘
                             │
          ┌──────────────────┼──────────────────┐
          │                  │                  │
          ▼                  ▼                  ▼
   ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
   │ Auth/User   │    │  Lottery    │    │   Ticket    │
```

# 5. Important lottery business rule

There is one area where I would be particularly strict:

**Randomness and winner selection must not be implemented casually.**

For example, don't write:

```java
Random random = new Random();
```

and call that a lottery engine.

Depending on the jurisdiction and whether this is a real-money lottery, the requirements around randomness, auditability, security, licensing, taxation, age restrictions, geographic restrictions, and draw integrity can be substantial.

For a learning/demo project, we can build a deterministic simulated draw engine.

For a real-money production system, we'd design the draw/audit mechanism around the applicable legal and regulatory requirements.

# 3. Lottery lifecycle

This is one of the most important parts of our design.

A lottery shouldn't simply have:

```text
ACTIVE / INACTIVE
```

We'll use:

```text
DRAFT
   ↓
SCHEDULED
   ↓
ACTIVE
   ↓
SALES_CLOSED
   ↓
DRAW_PENDING
   ↓
DRAW_COMPLETED
   ↓
SETTLED
```

There can also be:

```text
CANCELLED
```

Example:

```text
Mega Sunday
     │
     ▼
   DRAFT
     │
     ▼
 SCHEDULED
     │
     ▼
   ACTIVE
     │
     │ tickets sold
     ▼
SALES_CLOSED
     │
     ▼
DRAW_PENDING
     │
     ▼
DRAW_COMPLETED
     │
     ▼
   SETTLED
```

This prevents messy business logic later.

# 5. Ticket lifecycle

A ticket will have its own lifecycle.

```text
CREATED
   ↓
PAYMENT_PENDING
   ↓
PAID
   ↓
ISSUED
   ↓
DRAWN
   ↓
WINNER / NON_WINNER
   ↓
CLAIMED
```

For cancellation:

```text
ISSUED
   ↓
CANCELLED
```

But cancellation must be subject to lottery rules.

For example:

```text
Sales open
   ↓
Ticket purchased
   ↓
Ticket issued
   ↓
Sales closed
   ↓
Cancellation impossible
```

That's much safer than allowing an arbitrary `DELETE /tickets/{id}`.

# 3. Database-per-service

This is a major microservice principle.

Don't do this:

```text
                    ┌──────────────┐
                    │   MySQL      │
                    │              │
                    │ ALL TABLES   │
                    └──────────────┘
                      ▲ ▲ ▲ ▲ ▲
                      │ │ │ │ │
                     all services
```

Instead:

```text
Auth Service
     │
     ▼
 auth_db

Lottery Service
     │
     ▼
 lottery_db

Ticket Service
     │
     ▼
 ticket_db

Draw Service
     │
     ▼
 draw_db

Winner Service
     │
     ▼
 winner_db
```

This prevents one service from directly modifying another service's data.

# 13. Handling duplicate ticket purchases

This is a real-world problem.

Imagine two requests arrive simultaneously:

```text
Request A ─┐
           ├── Ticket number A
Request B ─┘
```

We need to prevent duplicate issuance.

We'll use a combination of:

```text
Database constraints
Transactions
Idempotency keys
Proper locking where necessary
```

For example:

```http
POST /api/tickets

Idempotency-Key: 5d8c9...
```

If the same request is submitted twice, the system shouldn't create two tickets.

# 14. Distributed transaction problem

Suppose:

```text
Ticket Service
     ↓
Payment
     ↓
Ticket created
     ↓
Kafka event
```

What happens if payment succeeds but ticket creation fails?

Or:

```text
Ticket created
     ↓
Kafka unavailable
```

We need to handle these failures.

We'll eventually use patterns such as:

### Transactional Outbox

```text
Ticket DB
 ┌──────────────────────┐
 │ tickets              │
 │ outbox_events        │
 └──────────┬───────────┘
            │
            ▼
       Kafka Publisher
            │
            ▼
          Kafka
```

This is much more reliable than:

```java
saveTicket();
kafka.send();
```

and assuming both always succeed.
